# ClrPalet-Watcom

Version 1.1

![ColorPalette ScreenShot](/doc/ColorPalette.png)

Modernized build of IBM's **Named Color Palette** Workplace Shell sample
(DEV-SAMPLES-WPS-ClrPalet, 1992/1993): the two SOM 1.0 `.SC` precompiler
classes were converted to **modern SOM IDL**, the tree was reorganized, and
the whole project now builds with **Open Watcom** on OS/2 2.x+ (ArcaOS).
Same treatment as `MBFolder-Watcom`; read that project's README first for
toolchain background.

## What it is

| Class | Parent | Purpose |
|---|---|---|
| `ColorPalette` | `WPColorPalette` | Palette of named colors, drag-and-drop like the system palette. Overrides cell painting (`wpPaintCell`) to draw arbitrary swatch shapes and cell editing (`wpEditCell`) to show its own color-picking dialog backed by the registered `ColorWheelControlClass` window control. |
| `StarColorPalette` | `ColorPalette` | Minimal subclass demo: overrides only `QuerySampleShape`, so every swatch is drawn as a star. |

Class chain:
`WPObject -> WPAbstract -> WPPalette -> WPColorPalette (wpconfig.dll) ->
ColorPalette -> StarColorPalette`

Both classes live in one DLL (`clrpalet.dll`). A PM test application
(`testapp.exe`) demonstrates the companion `COLOR_SAMPLE_CLASS` control,
which talks to an installed palette through the setup string
`CTRLHDL=<hwnd>` (see `clrsampl.c`, `clrpalet.c:wpSetup`).

## Changes in this release (v1.1)

### Interface definitions: SOM 1.0 `.SC` -> modern SOM IDL

| Original (`CLRPALET.SC/CSC`, spc/emitcsc) | This version (`idl/*.idl`, sc) |
|---|---|
| `class: ColorPalette, parent: WPColorPalette;` | `interface ColorPalette : WPColorPalette` |
| `data: { ... }` section | instance variables inside `implementation {}` |
| `override x, class;` lists | separate metaclass interface `M_ColorPalette : M_WPColorPalette` with its own override list |
| `passthru: C.ph;` IDs | hand-written `h\clrpids.h` (sc emits no `.ph`) |
| `passthru: C.ih;` globals/typedefs/includes | moved to the top of `src\clrpalet.c` / `src\clrstar.c` |

Conversion details worth remembering:

- **The `wpSelectCell` runtime hack is gone.**  1993: `WPPalette::wpSelectCell`
  was undocumented, so the sample installed its override at runtime with
  `_somOverrideSMethod()` inside `wpclsInitData` and invoked the parent
  through `_somFindMethod()` plus a `FNSELECTCELL` function-pointer cast.
  Toolkit 4.5 declares it publicly (`wppalet.idl:47-48`, releaseorder line
  69) and WPColorPalette itself overrides it (`wpclrpal.idl:59`), so our IDL
  just says `wpSelectCell: override;` and the code uses normal
  `parent_wpSelectCell(...)` resolution.  The method returns **void** in the
  modern bindings (the old code pretended BOOL).
- **Parameter attributes must be `in`, never `inout`, for pointer-to-buffer
  parameters kept from the original.**  sc maps `inout T*` to `T**` (an
  extra C indirection level); `QuerySampleShape(PPOINTL, PULONG)` passes a
  caller-owned array, so the faithful attribute is `in PPOINTL`.  Getting
  this wrong shows up as E1071/W100 "inconsistent levels of indirection".
- **Overridden method first parameter type = implementing class**, not the
  declaring class: SOM 1.0 generated `clrs_QuerySampleShape(ColorPalette *)`,
  modern sc generates `clrs_QuerySampleShape(StarColorPalette *)`.

Generated bindings (`h\clrpalet.ih/.h`, `h\clrstar.ih/.h`) are produced once
by `genbind.cmd`; they are not checked in and never regenerated by the
makefile (sc's emitted template `.c`s would overwrite the hand-ported code -
they are preserved as `release\sc_*_template.c` for reference instead).

### Implementation sources

- **PM/DOS/WPS header prelude**: the old precompiler emitted
  `INCL_WIN/GPI/DOS/DOSMODULEMGR/WINWORKPLACE/WPCLASS/WPFOLDER` + `<os2.h>`
  into the generated `.IH`. Modern sc doesn't, so both implementation files
  define them *before* including their `.ih` (otherwise `wpobject.h`'s
  `<pmstddlg.h>` fails on missing PM base types).  Also no
  `#define SOMLINK _System`: under Open Watcom `SOMLINK` stays empty
  (somltype.h has no `__WATCOMC__` case) and linkage comes from
  `#pragma linkage(..., system)` in the generated bindings; defining the
  macro yourself collides with the headers (E1100).
- **`wpEditCell` returns TRUE**: WPPalette declares `BOOL wpEditCell(...)`;
  the 1993 body fell off the end without returning a value.
- **No custom `_DLL_InitTerm`**: the original used the IBMC convention
  (`_DLL_InitTerm` calling `_CRT_init()` to capture the module handle).
  Open Watcom's OS/2 runtime provides no `_CRT_init` symbol and supplies its
  own default DLL initialization, so the custom init was dropped entirely;
  the module handle is queried lazily via `DosQueryModuleHandle("CLRPALET")`
  on first icon/dialog use (`GetClrPaletModHandle()` in `src\clrpalet.c`).
- **`SOMInitModule` added**: one entry point creating all three class
  objects (metaclass first), per IBM's animal-sample pattern; exported from
  the DLL.  `StarColorPaletteNewClass` is prototyped locally since
  `clrpalet.c` does not include the sibling's binding headers.
- `clrwheel.c`, `clrsampl.c`, `testapp.*` are toolchain-neutral C; only
  additions are `<stdio.h>` in clrsampl.c (sprintf prototype) and keeping
  the harmless IBMC `#pragma subtitle/page` listings pragmas in clrwheel.c.

### Class exports and imports

- **Exports**: nine class symbols plus `SOMInitModule`.  sc emits **no**
  `M_StarColorPalette*` bindings (clrstar.idl declares no metaclass) - the
  original DEF comment "SOM didn't give us a metaclass" holds just as true
  today, so those three lines stay commented out exactly like 1993.
- **Parent-class imports**: the sc-generated class-construction code
  references `WPColorPaletteNewClass`, `M_WPColorPaletteNewClass` and
  `WPPaletteClassData`, which live in **wpconfig.dll** (wppalet.idl:86,
  wpclrpal.idl:34).  somtk.lib only covers SOM.DLL itself, so the makefile
  runs IMPLIB over `src\wpconfig.def` to produce `release\wpconfig.lib` and
  links it alongside somtk.lib.

### Resources

- `clrpalet.rc`: added its own `#define INCL_WIN` + `<os2.h>` prelude (the
  rc compiler's preprocessor pass does not see CFLAGS; without it wrc dies
  with E049 near the first MIS_/SPBS_ token), swapped the defunct `.ph`
  include for `clrpids.h`, and referenced the icon as `src\clrpalet.ico`
  because wrc resolves resource-file paths against its working directory,
  not against `-i=` include dirs (E060 otherwise).
- Comment hygiene: rc/C comments may not contain `*/` inside prose
  (`MIS_*/MIA_*/...` terminates the comment early and produces bogus
  syntax errors on later lines).

### Build system

- **genbind.cmd** (REXX): locates the real SOM compiler (never bare `sc`,
  which Open Watcom shadows via `\WATCOM\BINW\SC.EXE`), invokes sc once per
  IDL with `-s "ih;h;c" -d h -I idl` so the bindings land directly in `h\`,
  deletes previous outputs *before* each run so "RESULT OK" can only mean
  freshly generated files, preserves sc's template `.c`s in `release\`,
  logs a summary to `release\genbind.log` and raw compiler output (stdout +
  stderr via sh.exe) to `release\sc_raw.log`.
- **Makefile.wat**: two targets - `release\clrpalet.dll` (clrpalet + clrstar
  + clrwheel objects, `-bd`, resources attached with wrc) and
  `release\testapp.exe` (testapp + clrsampl, plain PM program, no SOM).
  IMPLIB step builds the wpconfig import library automatically.
- **register.cmd / deregister.cmd** mirror the original INSTALL.CMD /
  UNINSTAL.CMD (same OBJECTIDs `<PALETFLDR>`, `<CLRPALET>`, `<STARCLRPALET>`),
  but register against the built DLL's full path so no LIBPATH edit is
  needed; deregister also calls SysDeregisterObjectClass, which the
  original forgot.
- All project text stays CRLF (OS/2 REXX and tools reject bare LF).

## Building

On the ArcaOS Dev VM (Open Watcom + toolkit at `C:\os2tk45`):

1. **Generate the SOM bindings (once per IDL change)**

       genbind

   Writes `h\clrpalet.ih/.h` and `h\clrstar.ih/.h` directly (sc option
   `-d h`; `-I idl` resolves `#include <clrpalet.idl>` from clrstar.idl).
   Logs: `release\genbind.log` (summary), `release\sc_raw.log` (raw).

2. **Compile and link**

       wmake -f Makefile.wat 2>&1 | tee compile.log

   Produces `release\clrpalet.dll` and `release\testapp.exe`.
   Path overrides: `wmake -f Makefile.wat SOMINC=... WPSINC=... SOMLIB=...`.

3. **Register and test**

       register        & rem registers both classes, creates desktop folder
       testapp         & rem sample-control demo (standalone)

   Then open **Palette Folder** on the desktop: two palettes appear; select
   a color, then double-click a swatch (or use `CSM_EDITRGBCOLOR`) to open
   the custom Edit Color dialog (color wheel + RGB spinbuttons).

4. **Uninstall**

       deregister

## Verification results (this release)

Build on ArcaOS Dev VM, Open Watcom 2.0.1:

- `release\clrpalet.dll` - 65368 bytes, resources attached, zero errors.
- `release\testapp.exe` - 10494 bytes, PM executable.

Warning-clean as of v1.1: the four warnings of the first build were dealt
with rather than tolerated.

- W1177 "Modifier repeated" at `sombtype.h(41)` - fires inside IBM's own
  header (`typedef somMethodProc SOMDLINK *somMethodPtr;`), which is
  read-only ground truth and was never built with Watcom. Silenced
  precisely via `-wcd=1177` in CFLAGS; every other warning still surfaces.
- W202 `MODID` unused in clrwheel.c - an SCCS what-string (`@(#)`) that is
  intentionally unreferenced. `#pragma disable_message(202)` turned out
  not to reach this diagnostic, so the line was removed (the pristine
  original stays in `orig\CLRWHEEL.C`).
- W202 `qmsg` unused in testapp.c - leftover from a WinGetMsg loop the
  sample no longer has (`WinDlgBox` runs a modal loop internally);
  declaration removed, note left in place.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `genbind`: "Syntax error: Unterminated quoted string" or bare-LF REXX errors | Text files lost CRLF (e.g. edited on Windows). All project text must stay CRLF for OS/2 tools. |
| `genbind`: sc resolves to `\WATCOM\BINW\SC.EXE`, ash syntax errors | Set `somBin` in genbind.cmd to the real SOM compiler dir (e.g. `C:\os2tk45\som\bin`). |
| `genbind`: "Unknown option o" in sc_raw.log | sc has no `-o` option (that token belongs to somipc's internal command line); use `-d <dir>` as genbind.cmd does. |
| `"override" has not been declared` in an .idl | Used CORBA-style `override a, b;`. SOM IDL wants `a: override;` per method. |
| E1071 / W100 "inconsistent levels of indirection" vs an .ih prototype | Stale bindings (rerun genbind) or an `inout` attribute on a buffer parameter (use `in`; see release notes). |
| E1100 macro redefinition of SOMLINK while compiling | Something `-d`efines SOMLINK. Remove it; let the pragma-based linkage work. |
| pmstddlg.h E1022 cascade | Missing PM prelude: `INCL_WIN` etc. + `<os2.h>` must precede `#include "*.ih"` (and be present in the `.rc` for wrc). |
| wrc E049 syntax error near SPBS_/MIS_ token | Resource script lacks its own `#define INCL_WIN` + `<os2.h>` prelude. |
| wrc E060 Can't find file "...ico" | Resource-file paths resolve against wrc's working directory; reference them relative to the makefile cwd (`src\clrpalet.ico`). |
| W1177 "Modifier repeated" at sombtype.h(41) | Known Watcom-vs-IBM-header quirk, expected; already suppressed via `-wcd=1177` (see Verification results). If you see it, your build used old flags. |
| Linker E2028 `M_StarColorPalette*` undefined | Those symbols don't exist - sc emits no bindings for classes without explicit metaclasses. Remove them from exports. |
| Linker E2028 `WPColorPaletteNewClass` / `WPPaletteClassData` / `M_WPColorPaletteNewClass` | Parent classes ship in wpconfig.dll; keep them listed in `src\wpconfig.def` (IMPLIB step supplies the import library). |
| Linker E3033 directive error near a symbol name | wlink rejected inline `IMPORT` directives; use the IMPLIB route instead. |
| Linker E2028 `_CRT_init` | IBMC-only symbol; don't define a custom `_DLL_InitTerm` under Watcom - let its default DLL init run (see release notes). |
| Registration succeeds but objects don't appear / WPS hangs on load | Stale class registration pointing at an older DLL path - run `deregister`, restart the WPS, rebuild, `register` again. Crashes land in `C:\POPUPLOG.OS2`. |
